# 多场景独立实现说明

## 为什么不做一个万能业务模型

Research 的“claim/evidence/conflict”与 Tutor 的“mastery/uncertainty/intervention”并不是同一种状态；Life 的实时事实还明确不能长期持久化，而 Character 的关系转移又是确定性状态机。强行统一只会制造大量可选字段、隐式语义和越权路径。

## 五个 vertical

| Vertical | 主要输入 | Durable State | 核心治理问题 |
|---|---|---|---|
| Agent | agent contracts + context | contracts/context/handoffs | 谁能把什么交给谁，接收方是否篡改 |
| Research | canonical claims | evidence/handoffs/deliveries | 反证丢失、provenance、最终交付绑定 |
| Tutor | learner observations | skill posterior / pedagogy / verifier | 提示后答对不能等价于独立掌握 |
| Life | explicit preference/plan | preference/plan/risk boundary | realtime 不长期存储，高风险升级 |
| Character | domain events | relationship state | 确定性关系状态演化、重复事件防重放 |

## 可以统一的部署体验

所有 vertical 都可以：

1. 使用同一个 SQLite 文件；
2. 使用相同 Session/Audit repository 基础设施；
3. 由一个 Gateway 对外服务；
4. 使用相同 revision/idempotency 错误语义；
5. 独立运行与独立测试。

因此“统一”发生在工程平台层，而不是业务语义层。
