# PPL 架构与边界

## 1. 分层

PPL 当前稳定体系分为六层：

1. **Foundation**：Core / Runtime / Profiles；定义语言、状态、确定性 resolve 和领域合同。
2. **Governance**：Multi-Agent Governance (MAG)；治理 Agent→Agent / Reviewer→user 的 delegation authority、context projection、information fidelity、canonical evidence binding 与受控 recovery。MAG **不是 orchestration framework**。
3. **Application**：Host / Life Binding / Observatory；承载真实 Agent 生命周期、领域约束和可观察性。
4. **Infrastructure**：Provider / Judge Transport；只负责模型与评估通道，不拥有业务状态。
5. **Integrations**：DeepSeek Harness Adapter 等特定宿主集成。
6. **Experience**：Experience Rule Evolution；把真实 episode 提炼为可 replay、可验证、可退休的确定性协议规则。

## 2. 权威顺序

- Host 负责真实模型调用、工具生命周期、delivery 与 durable mutation 的最终提交边界。
- MAG 的 Execution Graph 与 Authority Graph 分离；MAG 可以拒绝越权/失真 handoff，但不接管 scheduler、graph runtime、agent registry、queue 或模型生命周期。
- Profile/Binding 定义领域状态与约束；模型输出始终是 untrusted candidate。
- Judge 是外部语义门禁，但不能覆盖 Host-owned deterministic facts/state。
- Experience Rule 低于现有 PPL authority；只有 `validated` rule 才可在 `enforce` 模式执行。
- Observatory 只读，不提交状态。

## 3. Experience Rule Evolution 的位置

R1/R2 真实 A/B 证明：把 Gene 直接作为 runtime advisory prompt 不能稳定改善顶层用户可见 `message`。因此 GEP 被重新定位为：

```text
Real Episodes
  → Experience Distillation
  → Candidate Rule + provenance
  → deterministic replay / fault injection / real qualification
  → Validated Rule
  → Protocol / Judge / Repair / Regression asset
```

首个 Stable Rule 将 Host 已知的 `RESEARCH_CONFLICT_ERASURE` 失败模式编译为 pre-Judge Host-owned repair fast-path；未知错误仍交给 Judge，修复稿仍需经过正常 delivery gate。
